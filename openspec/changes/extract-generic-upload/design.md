## Context

现有 `files` 已提供稳定 UUID，但数据库读取和 S3 适配器位于 `documents/file`，上传动作引用文档权限并在完成时创建版本。管理端 Uppy 已支持普通与 Multipart 上传，不能因模块独立而丢失恢复和幂等能力。工作区已有文档事务与权限重构，本变更在其基础上增量实施。

## Goals / Non-Goals

**Goals:**

- 以 `files.file_id` 作为对外 key，业务不保存 URL 或物理对象位置。
- 通用上传完成与文档绑定分开提交、分别重试。
- 业务授权后通过 upload 生成 URL、读取流和清理文件。
- 预览产物与源文件统一存储管理，保持发布、取消和清理语义。

**Non-Goals:**

- 不引入通用引用表、多存储提供者注册框架或新的外部依赖。
- 不开放任意 key 换取 URL 或物理删除的客户端接口。
- 不自动清理已验证但尚未绑定的文件，不改变通用任务运行时。

## Decisions

### 文件句柄与存储适配器隔离

`Upload` 组合内部 S3 适配器，对外以 key 执行 put、getInfo、getReadableSource、getUrl、open 和受控物理删除；对象位置只在内部查询。共享文件与传输类型放在通用类型出口，文档版本绑定结果仍属于 documents。

### 保留通用上传会话

initialize、分片签名、分片恢复、complete、abort 和 status 移入 `/upload`；服务端用途策略约束文件种类与大小，会话持久化用途供恢复与幂等校验。所有权校验在 upload 内实现并遵循管理员全权限规则。

### 上传对象固化

客户端只向临时路径写入。完成操作领取 completing 状态后，将临时对象复制到唯一最终路径，再验证最终对象并发布 verified 文件；旧 PUT 地址只影响临时对象。完成重试复用同一文件句柄，失败删除本次最终对象并收敛文件和会话状态。大文件以存储分片保留现有能力，当前大小限制不超过 CopyObject 上限。

### 文档绑定独立

文档绑定接口接收 key 和可选 documentId，在文档事务内创建/复用版本与入队。通用会话不保存 documentId。前端持久化 UploadedFile 与 DocumentUploadResult 两个结果；绑定失败重试时不重新上传，目标文档在首次初始化时冻结。

### 预览引用与清理

预览页面保存 file_id，转换器只接受元数据和 open 工厂。生成页面通过 upload.put 保存，发布失败清理未引用的新页面，发布成功清理被替换的旧页面。文档物理清理先删除对象，再在领域事务内解除引用并清理文件记录；对象删除可幂等重试，不因半途失败丢失清理线索。

## Risks / Trade-offs

- [表结构变化] → 明确列出会话、预览页面表和用途字段变更，按项目既有 reset 规则部署，不自动执行破坏性迁移。
- [业务权限与上传者不同] → 不暴露裸 key 的通用读取接口，文档先校验业务权限再调用内部能力。
- [客户端恢复格式变化] → 升级 Uppy 持久化命名空间，避免把旧会话当作新语义恢复。
- [临时直传 URL 未到期] → 固化最终对象后不再用于业务读取；临时对象残留由存储生命周期规则或后续清理处理。
- [已验证孤儿文件] → 首版保留，避免无法证明无引用时误删业务文件。

## Migration Plan

1. 部署前停止旧上传流程，按 reset 流程处理 `file_upload_sessions`、`files` 新用途字段及双层页面表的列变更；历史文件保留需先备份并转换引用。
2. 服务端和管理端同步部署，使用通用 upload 路由与独立文档绑定接口。
3. 回滚需要同时恢复旧表结构、服务端和管理端，不混用两种完成响应。
